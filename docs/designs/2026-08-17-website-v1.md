# GPU Safari Website v1 Design

## Purpose

GPU Safari should feel like a learning experience before it feels like a code repository. The first public website will help Python developers who are new to GPUs build an accurate mental model of parallel work, see it happen, and optionally run the same idea on real hardware.

The first release is intentionally small: one excellent guided expedition, a preview of future trails, and a clear path into the open-source project.

## Audience

The primary learner knows basic Python but has little or no GPU experience. Explanations should also remain accessible to curious non-specialists without making the presentation childish. New terms are introduced through a concrete visual before they appear as platform vocabulary.

## Product principles

- Give the learner an immediate visual success before asking them to install anything.
- Teach portable concepts, then map them accurately to Metal, Triton, CUDA, and later ROCm.
- Clearly distinguish simulations from measured hardware execution.
- Make local or paid execution optional and explicit.
- Keep the public website static, fast, accessible, and hosting-neutral.
- Keep GitHub as the source, experiment gallery, and contributor workspace.

## Version-one scope

The release contains:

- a guided-expedition homepage;
- the complete **Paint Pixels in Parallel** lesson;
- a lightweight trail map for available and upcoming lessons;
- optional Apple Silicon and NVIDIA cloud execution guidance;
- links to experiments, contribution documentation, and GitHub.

The release does not contain accounts, a database, analytics, persistent learner profiles, a server-side application, or automatic cloud execution.

## Information architecture

The public routes are:

- `/` — guided-expedition homepage;
- `/learn/paint-pixels/` — first interactive lesson;
- `/trails/` — available and upcoming learning paths.

Lesson metadata is the single source of truth for titles, summaries, estimated time, difficulty, ecosystem labels, route, and availability. The homepage and trail map consume the same metadata so a new lesson is not registered in multiple hand-maintained lists.

The initial implementation remains plain static HTML, CSS, and JavaScript around the existing learning lab. The metadata and route boundaries should remain clean enough to migrate to a content framework when the number of lessons makes that useful. Version one does not add a framework preemptively.

## Homepage experience

The homepage leads with the promise **See parallel work come alive** and one primary action: **Start the 10-minute lesson**. It briefly previews the learning loop—predict, visualize, run, explain—without presenting a large catalog or requiring visitors to understand GPU ecosystem terminology.

Below the primary action, the page shows:

- what the learner will understand;
- the first expedition and its duration;
- a preview of future CUDA, Apple GPU, Triton, ROCm, memory, profiling, and AI-workload trails;
- a concise open-source contribution entry point.

Future trails are visibly marked as upcoming. They must not look clickable or complete when they are not available.

## Lesson journey

Every lesson follows the same seven-stage contract:

1. **Story** — introduce a concrete analogy.
2. **Predict** — ask the learner to commit to an outcome.
3. **Simulate** — show independent workers performing the task.
4. **Code** — reveal the smallest relevant kernel.
5. **Run** — optionally execute the idea on measured hardware.
6. **Explain** — map the visual model to platform terminology.
7. **Challenge** — change one variable and observe the result.

The required journey ends successfully without hardware, installation, an account, or payment. Real execution appears as an optional **Take it further** section after the core idea is understood.

## Execution model

The website has three execution levels:

### Concept simulation

The static browser lesson animates the work mapping and never presents simulated timing as measured performance.

### Local Apple GPU

An optional loopback companion runs the existing custom Metal kernel through MLX. The website detects the companion, labels the result as measured execution, and consumes the provider-neutral result contract.

### Cloud GPU

An optional provider adapter runs the equivalent workload on NVIDIA hardware. Modal is the first adapter. Before any launch, the interface identifies the provider and accelerator and requires explicit confirmation that the run may consume quota or incur a charge.

Future cloud platforms use the same result contract. The static website does not embed provider credentials or start remote compute itself.

## Result contract

Measured backends return the existing provider-neutral fields for provider, device, implementation, workload, correctness, latency, and checksum. UI components depend on this contract rather than provider-specific output.

Timing appears only when returned from real hardware. A simulation, unavailable companion, failed launch, or malformed response must never be converted into a plausible-looking measurement.

## Visual direction

The visual identity is a technical expedition:

- deep forest and navy foundations;
- bright trail-green accents for progress and primary actions;
- warm map-like surfaces for explanations;
- large, approachable typography;
- restrained motion that demonstrates work or state changes.

The result should feel curious and technically credible, not childish, corporate, or game-like. Existing lesson interaction patterns should be reused so the homepage and lesson feel like one product.

## Accessibility and responsive behavior

All core interactions work with keyboard and screen readers. Focus states remain visible, selected answers are not communicated by color alone, and animation respects reduced-motion preferences. The lesson remains understandable without motion.

Homepage, trail map, lesson navigation, work visualization, code, and result cards must work at phone and desktop widths without horizontal page scrolling. Code blocks may scroll internally when required.

## Safety and failure behavior

- Static hosting clearly labels concept simulation and never fabricates hardware capabilities.
- Unsupported local hardware receives an explanation and a next step rather than a broken control.
- Cloud controls remain disabled until prerequisites and confirmation are satisfied.
- Loopback requests retain host, origin, content-type, and body-size protections.
- Browser-facing errors remain generic; detailed provider diagnostics stay in the local terminal.
- Generated pages and documentation contain no account IDs, private run URLs, credentials, or provider workspace identifiers.

## Deployment

The website builds to static files with repository-relative internal URLs. It can be hosted by GitHub Pages, Cloudflare Pages, Vercel, or a basic static server without changing application behavior.

GitHub Pages is the recommended first deployment because the project already lives on GitHub and version one requires no server runtime. Provider-specific configuration should remain minimal and isolated from site content.

## Verification

Automated checks cover:

- route and lesson-metadata integrity;
- lesson state transitions and work mapping;
- keyboard and accessible-name behavior where practical;
- reduced-motion and responsive CSS contracts;
- static-hosting capability fallback;
- local Apple execution contract;
- guarded cloud confirmation and error sanitization;
- absence of private provider identifiers in public files.

Manual verification covers the homepage-to-lesson journey at phone and desktop widths, keyboard-only navigation, the static fallback, and one real Apple Silicon execution. A paid cloud run is optional and requires separate explicit authorization.

## Success criteria

Version one succeeds when a new GPU learner can:

1. understand why independent work suits a GPU;
2. complete the first visual lesson without setup;
3. distinguish a concept simulation from a measured run;
4. explain the relationship and differences among Metal threadgroups, Triton programs and vector lanes, and CUDA blocks and threads;
5. find a safe next step for local hardware, cloud hardware, another trail, or contributing.
